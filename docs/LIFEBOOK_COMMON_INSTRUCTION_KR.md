# MyDocuMgm(나의 생활북) 공통 운영·구현 지시문

## 1. 적용 방법

이 문서는 MyDocuMgm의 모든 단계에 항상 적용되는 상위 지시문이다.

- Codex 작업마다 이 문서와 현재 단계 지시문을 함께 제공한다.
- 두 문서가 충돌하면 이 공통 지시문의 안전·범위·증거 규칙을 우선한다.
- 현재 단계 지시문에 없는 기능은 구현하지 않는다.
- 이전 단계에서 완료된 작업은 `ALREADY_DONE`으로 확인만 하고 반복하지 않는다.
- 사용자 승인 없이 다음 단계로 넘어가지 않는다.

### MyDocuMgm 확정 기준

- 프로젝트와 C# namespace는 `MyDocuMgm` 및 `MyDocuMgm.*`를 사용하고, 사용자 표시명은 `나의 생활북`을 사용한다.
- SQL Server는 `localhost\MSSQLSERVER01`, DB는 기존 `MyDocuMgm`, Windows 인증을 사용한다.
- 자료 루트는 프로젝트 상대경로 `data\MyDocuMgmData`이며 실제 폴더 생성은 명시적으로 승인된 단계에서만 수행한다.
- Codex 샌드박스에서는 Windows 인증 DB 연결을 수행하지 않는다. DB 적용과 통합 검증은 사용자가 PowerShell 또는 SSMS에서 수행한다.
- AI는 설치된 Codex의 Phase 2 자동 분석과 ChatGPT의 사용자 주도 수동 검토만 허용한다. 유료 AI API, OpenAI API 자동 연동, 별도 로컬 모델 설치는 제외한다.

## 2. 제품 목표

PC에서 인스타그램 등 웹 자료를 수집·분석·정리하고, 로컬에 보관한 뒤 블로그 게시용 초안을 생성하는 개인용 Windows 로컬 웹 앱을 만든다.

기준 흐름:

> URL 입력 → 원문·영상·댓글 분석 → 요약·분류·태그·캡처 후보 생성 → 사용자 검토 → MSSQL 및 로컬 폴더 저장 → 블로그 초안 생성 → 사용자가 PC에서 게시

휴대폰은 게시된 블로그를 열람하는 용도다. 로컬 비공개 자료의 모바일 동기화는 현재 범위가 아니다.

## 3. 고정 기술 조건

- 프런트엔드: Vue 3 + TypeScript
- 백엔드: ASP.NET Core Web API
- ORM: Entity Framework Core
- DBMS: 로컬 Microsoft SQL Server 2022
- 실행: Windows PC의 `localhost`
- 이미지·첨부파일: PC 로컬 폴더
- DB에는 파일 바이너리가 아니라 상대경로와 메타데이터만 저장
- 외부 클라우드 DB·이미지 저장소·회원가입·다중 사용자 제외

설치된 런타임과 기존 프로젝트 버전을 확인한 뒤 호환되는 지원 버전을 제안한다. 사용자의 승인 없이 프레임워크 버전을 임의 선택하거나 변경하지 않는다.

## 4. 고정 메인 분류

콘텐츠는 정확히 하나의 메인 분류를 가진다.

| 순서 | 코드 | 표시명 |
|---:|---|---|
| 1 | `PLACE` | 가볼곳 |
| 2 | `COOKING` | 요리 |
| 3 | `EXERCISE` | 운동 |
| 4 | `CLEANING_LAUNDRY` | 청소&세탁 |
| 5 | `TRAVEL` | 여행 |
| 6 | `PHOTO` | 사진 |
| 7 | `STUDY` | 공부 |
| 8 | `PRODUCT` | 제품 |
| 9 | `PHONE_COMPUTER` | 폰&컴 |
| 10 | `TIP` | 팁 |
| 11 | `OTHER` | 기타 |

규칙:

- 분류 코드와 태그를 혼합하지 않는다.
- AI 추천은 가능하지만 사용자가 최종 확정한다.
- 확신이 낮으면 자동 확정하지 않고 `검토 필요`로 표시한다.
- `기타`를 불확실한 분석의 자동 배출구로 사용하지 않는다.
- 세부 해시태그는 다중 입력을 허용하고 정규화해 중복을 막는다.

## 5. 상태와 공개 범위

콘텐츠 상태:

- `INBOX`: 수집 완료, 미검토
- `REVIEW_REQUIRED`: 불확실 항목 확인 필요
- `READY`: 사용자 검토 완료
- `DRAFTED`: 블로그 초안 생성
- `PUBLISHED`: 게시 완료
- `ARCHIVED`: 보관

별도 속성:

- 즐겨찾기
- 해볼 것
- 해봄
- 비공개 전용
- 공개 가능

상태값을 해시태그로 구현하지 않는다. 공개 가능 여부는 콘텐츠와 이미지 각각 관리한다.

## 6. 분류별 핵심 필드

- 가볼곳: 장소명, 주소, 지역, 운영시간, 휴무, 비용, 주차, 지도 URL, 방문 상태
- 요리: 재료·분량, 도구, 시간, 난이도, 단계, 보관법, 대체 재료
- 운동: 부위, 준비물, 횟수, 세트, 시간, 자세, 주의사항
- 청소&세탁: 대상, 준비물, 세제·제품, 순서, 금지사항, 재질별 주의
- 여행: 국가·지역, 일정, 비용, 교통, 예약, 준비물, 주의사항
- 사진: 촬영 대상, 기기, 설정, 구도, 조명, 보정
- 공부: 주제, 핵심 개념, 학습 단계, 참고 자료, 복습 항목
- 제품: 제품명, 브랜드, 용도, 장단점, 가격, 구매처, 사용 조건, 주의사항
- 폰&컴: 기기·OS, 문제·목적, 설정 경로, 실행 단계, 원복 방법, 위험도
- 팁: 적용 상황, 준비물, 방법, 기대 효과, 한계와 주의사항
- 기타: 자유 제목, 요약, 상세 내용, 체크리스트

가격·주소·운동 횟수·재료 분량·제품 효능 등 오류 위험이 큰 정보는 근거와 사용자 확인 상태를 기록한다.

## 7. DB 공통 원칙

- 확정 DB명은 `MyDocuMgm`이다.
- 동명 DB가 존재하면 덮어쓰거나 마이그레이션하지 않고 즉시 보고한다.
- 인스턴스명과 인증 방식을 추정하지 않는다.
- 기본 키는 `uniqueidentifier`를 우선 검토한다.
- 시간은 UTC 저장, 화면에서 로컬 시간 변환을 원칙으로 한다.
- 동시 수정 보호를 위해 `rowversion`을 사용한다.
- 연결 문자열과 비밀값은 소스·문서·로그·Git에 기록하지 않는다.
- EF Core 마이그레이션은 생성 전 변경 SQL과 영향을 검토한다.
- DB 생성·마이그레이션·시드 변경은 해당 단계의 명시적 승인 범위에서만 수행한다.

최소 논리 엔터티:

- `Categories`
- `Contents`
- 분류별 상세 정보 구조
- `Tags`, `ContentTags`
- `MediaAssets`
- `SourceEvidence`
- `Publications` (Phase 4 이후)
- `ImportJobs` (Phase 2 이후)

분류별 상세 필드를 모두 무제한 JSON에 넣지 않는다. 검색·필터가 필요한 값은 명시적 컬럼 또는 상세 테이블로 설계한다. 제한적 JSON 보조 필드는 설계 근거와 검증 방법이 있을 때만 허용한다.

## 8. 로컬 파일 공통 원칙

권장 구조:

```text
data/MyDocuMgmData/
├─ media/
│  ├─ place/
│  ├─ cooking/
│  ├─ exercise/
│  ├─ cleaning-laundry/
│  ├─ travel/
│  ├─ photo/
│  ├─ study/
│  ├─ product/
│  ├─ phone-computer/
│  ├─ tip/
│  └─ other/
├─ temp/
├─ exports/
│  ├─ html/
│  ├─ markdown/
│  └─ blog-assets/
└─ backup/
```

규칙:

- 루트는 설정으로 지정하고 소스에 절대경로를 고정하지 않는다.
- DB에는 `media/cooking/...` 형태의 상대경로만 저장한다.
- `..`, 심볼릭 링크·재분석 지점 등을 통한 루트 이탈을 차단한다.
- 확장자뿐 아니라 MIME과 실제 파일 형식을 검증한다.
- 파일 크기 제한과 허용 형식을 둔다.
- 파일명 충돌을 피하고 SHA-256을 기록한다.
- 원본 캡처와 블로그용 파생 이미지를 구분한다.
- 임시 파일은 성공·실패·취소 후 정리한다.

DB와 파일 저장은 한쪽만 완료된 불일치를 탐지해야 한다. 임시 파일 → DB 처리 → 최종 파일 확정의 순서와 보상 처리 정책을 설계하고 테스트한다.

## 9. 수집·분석 공통 원칙

- 공개적으로 접근 가능한 URL만 처리한다.
- 로그인·비공개 콘텐츠·접근제한을 우회하지 않는다.
- 사용자 브라우저의 쿠키나 인증정보를 임의 추출·영구 저장하지 않는다.
- 원문 URL, 사이트, 작성자, 게시일, 수집 시각을 가능한 범위에서 보존한다.
- 영상 자막, 화면 텍스트, 본문, 대표 댓글을 서로 다른 근거 유형으로 보관한다.
- AI 생성 결과와 원문 사실을 구분한다.
- 불확실한 내용은 숨기지 않고 사용자 확인 대상으로 표시한다.
- 수집 실패 시 본문 붙여넣기, 댓글 붙여넣기, 이미지·영상 직접 선택을 제공한다.
- 같은 URL을 자동 덮어쓰지 않는다. 중복 경고 후 사용자가 결정한다.

## 10. 캡처·저작권 공통 원칙

- 영상에서 의미 있는 단계 후보를 추출한다.
- 유사 프레임을 중복 제거하고 사용자가 선택·정렬한다.
- 각 이미지에 단계·설명·공개 허용 여부를 기록한다.
- 캡처의 기본값은 `비공개 전용`이다.
- 블로그 초안에는 사용자가 공개 가능으로 표시한 이미지만 포함한다.
- 출처 URL과 작성자를 삭제하지 않는다.
- 무단 재게시를 편리하게 만드는 방향보다 인용·원문 연결·사용자 확인을 우선한다.

- 일반 텍스트
- Markdown
- HTML
- 정렬된 이미지 파일 묶음

기본 초안 구조:

## 12. 삭제·백업·복원

- 최초 버전은 soft delete 또는 휴지통을 우선한다.
- 콘텐츠 삭제 시 연결 파일을 즉시 영구 삭제하지 않는다.
- 내보내기 실패가 원본 콘텐츠를 변경해서는 안 된다.
- DB 백업과 `data\MyDocuMgmData` 폴더 백업을 함께 관리한다.
- 백업 매니페스트에 생성 시각, DB 백업 파일, 파일 범위·해시를 기록한다.
- DB만 또는 파일만 백업했을 때 완전 복원이 불가능함을 명시한다.
- 복원은 원본 운영 데이터를 덮어쓰기 전에 격리된 위치에서 검증한다.

## 13. Git·작업 범위 규칙

- 시작 시 저장소 루트, 브랜치, HEAD, worktree 상태를 기록한다.
- `AGENTS.md` 및 프로젝트 지시서를 먼저 확인한다.
- 기존 사용자 변경사항을 삭제·정리·되돌리지 않는다.
- 허용 경로 집합을 단계 시작 전에 고정한다.
- 승인되지 않은 파일 변경이 필요하면 작업을 중단하고 보고한다.
- `git reset --hard`, 무단 checkout, stash, clean을 금지한다.
- 커밋과 push는 단계 지시문이 명시적으로 허용할 때만 수행한다.
- 다른 프로젝트나 유사 이름의 저장소를 대신 작업하지 않는다.
- 보고서의 프로젝트명·절대경로·HEAD를 시작과 종료 시 대조한다.

## 15. 단계 게이트와 판정

- `PASS`: 승인 범위가 구현되고 필수 검증과 증거가 완료됨
- `HOLD`: 환경·승인·외부 조건 때문에 완료 판정 불가
- `REJECT`: 요구사항 위반, 데이터 위험, 필수 검증 실패

각 단계는 다음 순서로 수행한다.

1. 시작 기준선과 허용 범위 확인
2. 충돌·위험 보고
3. 승인 범위 구현
4. 관련 테스트
5. 브라우저·런타임 증거
6. 변경 경로와 잔여 위험 보고
7. 사용자 승인 대기
